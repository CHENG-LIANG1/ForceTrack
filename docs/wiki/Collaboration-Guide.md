# 协作与 PR 规范

## 分支与范围

1. 从最新 `main` 创建短生命周期主题分支。
2. 一个 PR 聚焦一个可独立验收的目标；不要顺手重构无关模块。
3. 工作区已有改动属于原作者，先确认范围并保留，不覆盖、不重置。
4. 当前仓库历史中既有 `dev` 也有 topic branch；新工作默认使用 topic branch，除非维护者明确要求走 `dev`。

示例：

```bash
git switch main
git pull --ff-only
git switch -c feature/short-topic
```

## 开工前审计

跨层功能先给出差距表：

| 结论     | 含义                   | 行动                 |
| -------- | ---------------------- | -------------------- |
| 已满足   | 代码和测试已符合要求   | 保留，只补必要证据   |
| 部分满足 | 主体存在但缺规则或验证 | 最小补齐             |
| 缺失     | 没有实现               | 新增                 |
| 不符合   | 与领域/技术规范冲突    | 修正并加回归         |
| 无法验证 | 缺运行环境或证据       | 明确限制，不宣称通过 |

ForceTrack 的演进要求保留合规工作，尤其不能为新 Schema 重写旧迁移契约，或为 UI 调整破坏既有领域规则。

## Commit

- Commit 使用祈使句，说明结果，例如 `Add project-scoped activity filters`。
- 将实现、测试和对应文档放在同一逻辑提交或一组清晰提交中。
- 提交前查看 `git diff --check` 和 `git status`，避免带入构建产物、报告或他人未完成改动。
- 不提交 `dist/`、Playwright report、coverage HTML 或本地缓存。

## PR 描述模板

```markdown
## 目标

一句话说明用户结果。

## 范围

- 做了什么
- 明确没做什么

## 关键决策

- 领域/数据/交互上的重要取舍

## 验证

- `pnpm check` — 通过
- `pnpm test:coverage` — 通过，列出关键阈值
- `pnpm test:e2e` — 通过，列出数量和浏览器
- 浏览器走查 — 浏览器、viewport、页面

## 风险与回滚

- 数据迁移、兼容性和已知限制
```

只填写实际执行过的验证。失败后修复的事实可以保留为有用的工程记录，但最终结果要明确。

## Review 清单

- 业务规则是否在 domain/reducer 中，而不是散落在组件里？
- URL 是否仍是当前项目真相源？是否使用 route builder？
- 业务存储是否只通过 Repository？旧 Schema 是否保持只读？
- `position` 与 `rank` 是否混用？Sprint 状态机是否被绕过？
- 可见控件是否来自 `src/components/ui`？Feature 是否直接 import Radix？
- 中英文资源、主题令牌、键盘路径和焦点恢复是否齐全？
- 测试是否覆盖持久化、刷新、项目隔离和失败恢复？
- 文档和验收证据是否与实际代码同步？

## 合并条件

- 需求与范围清楚。
- 相关自动化和完整质量门禁通过。
- 没有未解决的阻塞 Review。
- Schema/迁移变更具有回归证据。
- PR 合并后确认远端 `main` 包含目标提交。

当前没有 GitHub Actions 自动替代这些检查；合并者必须核对 PR 中的可复现证据。
